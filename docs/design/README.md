| 項目 | 内容 |

[仕様書](../spec/) の動きを実現する内部構造を定めます。各節の見出しに、対応する要件 ID を書きます。技術選定の理由は [設計判断の記録](../decisions/) にあります。

## 1. 全体構成

### 1.1 モジュール

1 つのクレート（`bunsan_souzou`）を、関心ごとのモジュールに分けます。

```
src/
├── main.rs        … 起動処理。ui を呼び出すだけ
├── model/         … 作品のデータ構造と、座標計算・当たり判定などの純粋な処理
├── storage/       … 作品フォルダの読み書き（JSON）
├── history/       … 履歴操作。git コマンドを呼び出す
├── assets/        … 素材の管理（ハッシュ値の計算、素材一覧の保存場所）
├── p2p/           … 素材の公開・受け取り（Iroh）
└── ui/            … 画面（egui）。道具・パネル・ダイアログ
```

### 1.2 依存の向き

```
ui ──→ model
 │ ──→ storage ──→ model
 │ ──→ history
 │ ──→ assets
 └──→ p2p ──→ assets
```

- `model` はどのモジュールにも依存しません。画面・ファイル・通信から切り離し、単体テストしやすくします。
- `ui` だけが全体を組み合わせます。`history`・`p2p` は画面のことを知りません。

### 1.3 P2P の検証用プログラム

本体に組み込む前に、`examples/p2p_spike.rs` で「2 台の PC 間でハッシュ値を指定して画像を 1 枚受け渡す」ことを確かめます。`cargo run --example p2p_spike` で実行します。

## 2. 作品フォルダ（R-014・R-022・R-050・R-051・R-102）

```
作品フォルダ/
├── .git/
├── .gitattributes
├── work.json                … 作品の情報
├── layout.json              … コマ割り
├── panels/
│   └── <コマ ID>.json       … コマ内容（1 コマ 1 ファイル）
└── assets/
    └── <ハッシュ値>.png     … 貼った素材
```

- コマ割り（`layout.json`）とコマ内容（`panels/`）を別ファイルにすることで、コマ割りの変更とコマ内容の変更が Git 上でも別ファイルの変更になります。別々の履歴系統で行った変更は、競合せずに統合できます（仕様書 7.5、完成の定義の手順 9）。
- 素材のファイル名はハッシュ値なので、同じ素材は同じファイル名になり、統合時に競合しません。
- `.gitattributes` は作品の作成時に次の内容で作ります。PC 間で改行コードがそろい、PNG が文字データとして扱われるのを防ぎます。

  ```
  *.json text eol=lf
  *.png binary
  ```

## 3. データ形式（R-001・R-010〜R-014・R-020〜R-022）

座標の単位は、ページの幅を 1820 とした値（B5 の 0.1 mm 単位）です。ページの大きさは 1820 × 2570 です。

### 3.1 work.json

```json
{
  "format_version": 1,
  "page": { "width": 1820.0, "height": 2570.0 }
}
```

`format_version` は保存形式の版です。形式を変えたときに上げ、古い形式を読み込む処理を分けられるようにします。

### 3.2 layout.json（コマ割り）

```json
{
  "panels": [
    {
      "id": "3f2b8c1e-0d7a-4e5b-9c61-2a8f4d7e9b10",
      "frame": { "x": 100.0, "y": 100.0, "width": 800.0, "height": 600.0 },
      "view": { "offset_x": 0.0, "offset_y": 0.0, "scale": 1.0 }
    }
  ]
}
```

| 項目 | 内容 | 対応 |
| --- | --- | --- |
| `panels` の並び | 読み順。先頭が 1 番 | R-013 |
| `id` | コマ ID（UUID v4）。コマ内容のファイル名に使う | R-014 |
| `frame` | コマの枠の位置と大きさ（ページ座標） | R-010・R-011 |
| `view` | コマ内容の表示範囲。ずらす量と拡大率 | R-012 |

コマ ID をランダムな UUID にするのは、別々の履歴系統で同時にコマを作っても ID が重ならないようにするためです。

### 3.3 panels/<コマ ID>.json（コマ内容）

```json
{
  "assets": [
    { "hash": "b3a1…", "x": 50.0, "y": 40.0, "scale": 0.5 }
  ],
  "strokes": [
    { "points": [[10.0, 20.0], [12.5, 21.0], [15.0, 23.5]] }
  ]
}
```

| 項目 | 内容 | 対応 |
| --- | --- | --- |
| `assets` | 貼った素材。`hash` は `assets/` 内のファイル名、位置と拡大率はコマ内容座標 | R-020・R-021 |
| `strokes` | 線。点の座標の並び（コマ内容座標） | R-001 |

- 描画順は `assets` → `strokes`（素材が下、線が上）。
- 線の太さ・色は v0.1.0 では固定なので、データに持たずコードの定数にします。

### 3.4 座標の変換（R-012）

コマ内容座標 `p` からページ座標 `q` への変換：

```
q = frame の左上 + view.offset + p × view.scale
```

画面に描くときは、さらにページ座標からキャンバスの画面座標へ変換します（ページをウィンドウに収める拡大率と位置）。逆変換で、マウスの画面座標からコマ内容座標を求めます。変換は `model` に置き、単体テストします。

## 4. 描画（R-001・R-002）

- キャンバスは egui の `Painter` で描きます。コマごとに `frame` の範囲で切り抜き（`with_clip_rect`）、はみ出した部分を表示しないようにします。
- **ペン**：ドラッグ開始時に、マウス位置を含むコマを探し、そのコマに新しい線を追加します。ドラッグ中は点を追加し、前の点との距離が一定未満の点は間引きます。
- **消しゴム**：ドラッグ中、マウス位置（コマ内容座標）から各線の各線分までの距離を求め、半径以内の線を削除します。

## 5. 素材（R-020〜R-022・R-030〜R-032）

### 5.1 ハッシュ値

素材は BLAKE3 のハッシュ値で識別します。Iroh が使うハッシュ値と同じなので、P2P の素材 ID と作品フォルダ内のファイル名が同じ値になります。

### 5.2 素材一覧の保存場所

手元の素材（公開した素材・受け取った素材）は、利用者ごとのデータフォルダ（Windows では `%APPDATA%\bunsan_souzou\assets\`）に `<ハッシュ値>.png` で保存します。

### 5.3 貼り付け

素材一覧（またはファイル）から貼るとき、PNG を作品フォルダの `assets/<ハッシュ値>.png` にコピーし、コマ内容の `assets` に追加します。画像は `image` クレートで読み込み、egui のテクスチャにして表示します。

## 6. P2P（R-030〜R-032）

- Iroh と iroh-blobs を使います。
- **公開**：PNG を iroh-blobs の保存領域に追加し、得られるチケット（接続先の情報とハッシュ値を含む文字列）を素材 ID として表示します。
- **受け取り**：素材 ID（チケット）を解析して接続し、ハッシュ値を指定して取得します。iroh-blobs は受信中に BLAKE3 で検証するので、改ざんされたデータは受け取れません（R-032）。取得後、素材一覧の保存場所に書き出します。
- **非同期処理**：Iroh は非同期（tokio）で動くため、別スレッドで tokio を動かし、画面とはチャネル（`std::sync::mpsc`）で命令と結果をやりとりします。通信中も画面は固まりません。
- iroh・iroh-blobs の具体的な API は版によって変わるため、検証用プログラムで確かめてからこの節に追記します。

## 7. 履歴（R-040〜R-045）

### 7.1 履歴操作と git コマンドの対応

`history` モジュールが、仕様書の操作を git コマンドに対応させます。

| 操作 | git コマンド | 対応 |
| --- | --- | --- |
| 作品の作成 | `git init` | R-050 |
| 履歴更新 | `git add -A` → `git commit -m <メッセージ>` | R-040 |
| 変更の有無 | `git status --porcelain` | R-040・R-043 |
| 履歴一覧 | `git log --format=%H%x1f%s%x1f%cI` | R-041 |
| 過去の状態を見る | `git show <ハッシュ>:<ファイル>` でファイルを読み、表示専用で描く | R-042 |
| この状態に戻す | `git restore --source=<ハッシュ> --staged --worktree -- .` → 履歴更新 | R-042 |
| 履歴系統の一覧 | `git branch --format=%(refname:short)` | R-043 |
| 分岐 | `git switch -c <名前>` | R-043 |
| 切り替え | `git switch <名前>` | R-043 |
| 統合 | `git merge --no-ff <名前>` | R-044 |
| 競合したファイル | `git diff --name-only --diff-filter=U` | R-044 |
| こちら／あちらを採用 | `git checkout --ours <ファイル>` / `git checkout --theirs <ファイル>` → `git add <ファイル>` | R-044 |
| 統合を完了 | `git commit --no-edit` | R-044 |
| 統合を中止 | `git merge --abort` | R-044 |
| アップロード先の設定 | `git remote add origin <場所>`（設定済みなら `git remote set-url`） | R-045 |
| アップロード | `git push -u origin <今の履歴系統>` | R-045 |
| 初回ダウンロード | `git clone <場所> <保存先>` | R-045 |
| 継続ダウンロード | `git pull --no-rebase origin <今の履歴系統>` | R-045 |

- 区切り文字 `%x1f`（ユニットセパレーター）は、メッセージに含まれにくい文字として使います。
- 「この状態に戻す」は、`git restore` で作品を過去の状態にしてから新しい履歴を作ります。それまでの履歴はすべて残ります。

### 7.2 作者名とメールアドレス

履歴更新の前に `git config user.name` と `git config user.email` を確認し、未設定なら画面で尋ねて、作品フォルダのリポジトリに `git config --local` で設定します。

### 7.3 コマンドの実行

`std::process::Command` で `git` を実行し、終了コードが失敗なら標準エラー出力の内容をエラーとして返します。git の出力を利用者向けの言葉に置き換える処理は `ui` に置きます。

## 8. 画面（ui）

### 8.1 状態

```rust
struct App {
    work: Option<OpenWork>,   // 開いている作品（作品フォルダのパス・データ・未保存の変更の有無）
    tool: Tool,               // 選んでいる道具
    selection: Selection,     // 選択中のコマ・素材
    viewing: Option<String>,  // 過去の状態を表示中なら、その履歴のハッシュ
    history_panel: HistoryPanelState,
    p2p: P2pHandle,           // P2P スレッドとのチャネル
    status: String,           // 状態表示の文字列
}

enum Tool { Pen, Eraser, Panel, View, Asset }
```

### 8.2 日本語フォント

egui の標準フォントに日本語が含まれていないため、起動時に Windows の日本語フォント（`C:\Windows\Fonts\YuGothM.ttc`、なければ `meiryo.ttc`）を読み込んで設定します。PC に入っているフォントを使うので、フォントファイルを配布物に含める必要がありません。

## 9. エラー処理とテスト

- エラーは `anyhow::Result` で呼び出し元へ返し、`ui` で状態表示に出します。
- `model`：座標変換・当たり判定を単体テストします。
- `storage`：保存して読み込むと同じデータに戻ることをテストします。
- `history`：一時フォルダ（`tempfile` クレート）にリポジトリを作り、履歴更新・分岐・統合・競合をテストします。コマ割りとコマ内容を別々の履歴系統で変えて、競合せずに統合できることもテストします。
- `p2p`：検証用プログラムで手動で確認します。

## 11. 実装の順序

| 段階 | 内容 | 要件 |
| --- | --- | --- |
| M0 | P2P の検証用プログラム | R-030〜R-032 |
| M1 | 作品の作成・保存、1 コマへの描画と消しゴム | R-001・R-002・R-050・R-051 |
| M2 | コマ割り（作成・移動・大きさ・表示範囲・読み順） | R-010〜R-014 |
| M3 | 履歴（履歴更新・一覧・表示・戻す・分岐・統合・アップロード・ダウンロード） | R-040〜R-045 |
| M4 | 素材の貼り付け | R-020〜R-022 |
| M5 | P2P を本体に組み込み、完成の定義の流れを通す | R-030〜R-032 |

M0 は M1 と並行して進められます。各段階は、段階ごとにブランチとプルリクエストを分けます。
