# インターフェースと実装を分け、クレートで区切る

- 日付：2026-10-17
- 状態：採用

## 背景

分散創造は、描画・保存・履歴管理（git）・P2P（Iroh）という性質の違う部品を組み合わせる。git コマンドの呼び出しや Iroh の API は、版の変化や将来の置き換え（構想の独自形式・自前の中継サーバーなど）が見込まれる。部品どうしが密に結びつくと、1 つの変更が全体に波及し、テストにも本物の git や通信が必要になる。

## 判断

- 外の世界（ファイル・保存形式・履歴管理・素材置き場・P2P・ID の生成）とのやりとりを、**インターフェース（ports のトレイト）**として定義する。
- 実装は**アダプター**として別のクレート（store-json・fs・vcs-git・exchange-iroh）に置く。
- 中心部（domain・app）はインターフェースだけを知る。実装を組み合わせるのは組み立て役（bunsan-souzou）だけとする。
- 部品の境界を、モジュールではなく **Cargo のワークスペースのクレート**で区切る。

詳細は [設計書の全体構成](../design/architecture.md) にある。

## 理由

- **差し替えやすい**：P2P の仕組みや保存形式を変えても、中心部と画面は変わらない。
- **テストしやすい**：中心部を、メモリ上で動く偽物の実装（testkit）と組み合わせてテストできる。git や通信がなくても、速く・決まった結果で動く。
- **規則を守りやすい**：クレートは `Cargo.toml` に書いた依存先しか使えないため、依存の規則（例：画面から git を直接呼ばない）をコンパイラが守らせる。

## 影響

- クレートの数が増え（10 個）、最初の骨組みを作る手間が増える。M1 で骨組みを作る。
- ポートのトレイトは `Send + Sync` で、同期の形で定義する。非同期処理が必要な実装（Iroh）は、内部で非同期の実行環境を持つ。
- 新しい外部とのやりとりを加えるときは、先に ports にトレイトを加え、その後でアダプターを作る。
